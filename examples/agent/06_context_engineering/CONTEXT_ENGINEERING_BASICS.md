# 上下文工程基础知识

## 1. 什么是上下文工程

上下文工程就是在每次调用模型前，决定“给模型看什么、不给模型看什么、按什么顺序给它看”。

普通聊天接口经常只做：

```text
system prompt + user message
```

但 Agent 通常要处理更多信息：

```text
system prompt
+ 当前用户问题
+ 最近历史消息
+ RAG 检索资料
+ 工具 observation
+ 业务规则
+ 输出格式要求
```

如果这些内容没有管理好，模型会出现几类常见问题：

- 看不到关键信息，所以回答“资料不足”。
- 看到太多旧历史，所以误解当前任务。
- 看到低相关 RAG，所以被无关资料带偏。
- 看不到工具 observation，所以重复调用工具或编造结果。
- 上下文超过模型窗口，所以请求失败或被截断。

## 2. 上下文不是聊天历史

聊天历史只是上下文的一种来源。

上下文是“本次模型调用可见的信息包”。它可以包含历史消息，也可以包含 RAG、工具结果、用户偏好、系统规则和开发者约束。

企业项目里不要把所有历史直接塞给模型，原因有三个：

- 成本高：历史越长，token 越多。
- 延迟高：模型读取长上下文更慢。
- 干扰大：旧问题、旧资料可能和当前任务无关。

所以后端要做筛选。

## 3. 各类上下文的职责

### system prompt

system prompt 规定 Agent 的角色、边界、优先级和禁止事项。

在本模块里，它告诉模型：

- 你是电商售后 Agent。
- 优先依据工具 observation。
- 其次依据 RAG 资料。
- 再参考最近历史。
- 资料不足时不要编造。

### 当前用户问题

当前用户问题是本次请求的目标，必须保留。

如果预算太小，宁可丢掉历史，也不能丢掉当前问题。

### 历史消息

历史消息帮助模型理解对话承接，例如用户之前已经说过订单金额。

但历史消息优先级通常低于当前问题、工具 observation 和高相关 RAG。原因是历史里经常有闲聊、旧任务和重复信息。

### RAG sources

RAG source 是检索系统找到的资料片段。

它的价值是让模型根据资料回答，而不是只靠模型参数里的旧知识。

但 RAG 资料必须过滤相关性。低相关资料即使是真的，也可能干扰当前回答。

### 工具 observation

工具 observation 是工具执行后的结果。

例如：

```text
calculate_refund 返回 refund_amount=240
```

这类信息通常比历史和 RAG 更重要，因为它是 Agent 刚刚执行动作得到的新事实。

## 4. 为什么要有 token 预算

模型不是无限读取文本的。每个模型都有上下文窗口限制，真实项目还要考虑成本和延迟。

本模块使用教学版估算：

```python
ceil(len(text) / 2)
```

这不等于真实 token 数，只是帮助你先理解预算控制。生产项目会使用模型对应 tokenizer。

## 5. 上下文优先级

本模块采用的教学优先级是：

```text
system prompt
> 当前用户问题
> 工具 observation
> 高相关 RAG
> 最近历史消息
```

这个顺序不是永远固定的，但适合初学 Agent 时建立工程直觉。

判断依据是：

- 当前问题决定任务目标。
- 工具 observation 是刚得到的新事实。
- RAG 是外部知识约束。
- 历史消息只提供对话承接。

## 6. 为什么无关资料会干扰模型

大模型会尽量利用你给它的上下文。

如果用户问退款，你却把会员升级、营销活动、物流模板都塞进去，模型可能会错误地把问题理解成会员权益或活动优惠。

所以 RAG 不是“检索到就塞”，而是：

```text
检索 -> 过滤 -> 排序 -> 截断 -> 注入上下文
```

这就是上下文工程和普通字符串拼接的区别。

## 7. 本模块和后续模块的关系

本模块只负责一次请求前的上下文构造。

后续模块会继续扩展：

- 短期状态：把 Agent run 和 steps 保存下来。
- 记忆工程：把长期偏好和事实结构化保存。
- RAG 智能体：让 Agent 主动选择检索工具。
- 可观测性：记录每次上下文构造和模型调用 trace。
- 成本延迟并发：做更精确的 token、成本和性能控制。
