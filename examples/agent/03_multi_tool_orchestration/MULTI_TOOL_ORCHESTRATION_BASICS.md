# 多工具编排基础知识

## 1. 什么是多工具编排

多工具编排指的是：Agent 为了完成一个目标，不只调用一个工具，而是安排多个工具按顺序协作。

例如用户说：

```text
帮客户判断退款金额，并生成一段客服回复
```

后端不能只让模型随口回答。更可靠的流程是：

```text
查退款制度
-> 判断订单风险
-> 计算退款金额
-> 生成客服回复
```

这就是编排。

## 2. 为什么不能所有工具一起跑

有些工具互不依赖，可以并行。

例如：

- 查退款制度只需要 `policy_keyword`。
- 判断订单风险只需要 `days_since_purchase` 和 `item_problem`。

这两个工具都只依赖用户请求，所以理论上可以并行。

但有些工具必须串行。

例如：

- 计算退款金额需要先拿到退款制度。
- 生成客服回复需要先拿到退款金额。

如果前置数据还没准备好，后面的工具就不应该执行。

## 3. 什么是工具之间的数据传递

在本模块里，`planner.py` 会生成这样的参数：

```python
"policy": {"from_step": "policy", "field": "policy"}
```

意思是：

```text
当前工具的 policy 参数
来自 policy 这个步骤的输出
取输出里的 policy 字段
```

这就是工具之间的数据传递。

Java 类比：它像工作流里的变量引用，例如 `${policy.policy}`。

## 4. 为什么要记录 steps

多工具 Agent 最难排查的问题通常不是“接口崩了”，而是：

- 第一步查到了错误资料。
- 第二步算错了金额。
- 第三步拿错了字段。
- 某个工具失败后，后续步骤还继续执行。

所以每一步至少要记录：

- 工具名。
- 输入参数。
- 输出结果。
- 执行耗时。
- 成功、失败或跳过状态。
- 错误信息。
- 依赖的前置步骤。

有了这些记录，才能从最终回答一路倒查到出问题的工具。

## 5. 工具失败后应该怎么办

本模块先使用最简单的策略：

- 当前工具失败，记录 `failed`。
- 依赖它的后续步骤记录 `skipped`。
- 不依赖它的步骤仍然可以继续。

例如制度检索失败：

```text
policy failed
risk succeeded
refund skipped
reply skipped
```

这比直接让接口报错更好，因为你能看清楚失败影响了哪些步骤。

后续模块会继续学习更完整的恢复策略，例如重试、降级、人工确认和换工具。

## 6. 本模块和最小 Agent Loop 的区别

最小 Agent Loop 关注的是：

```text
模型决策 -> 工具调用 -> observation -> 下一轮决策
```

多工具编排关注的是：

```text
一个目标 -> 多个工具步骤 -> 步骤依赖 -> 数据传递 -> 失败影响范围
```

前者解决“Agent 怎么循环”，后者解决“Agent 怎么组织多个动作完成一件事”。
