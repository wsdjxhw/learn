# RAG 工具智能体基础知识

## 本模块解决的真实工程问题

上一节学的 RAG 长这样：用户调 `POST /ask`，后端固定检索一次，返回回答。这在演示里够用，但真实产品里不是这样工作的：

```text
用户的问题不总是需要检索。
用户可能闲聊，也可能问知识库外的事。
同一个问题，检索到的资料质量决定回答质量。
检索不到资料时，模型不能编。
```

真实 Agent 的工作方式是：**把检索变成模型可以主动调用的工具**，由 Agent（模型 + 后端策略）决定：

```text
这个问题需不需要检索？
需要的话，检索词是什么？
检索到的资料怎么进入回答？
检索不到怎么办？
```

本模块就是把模块 04 的 RAG 能力，从“一个固定的 /ask 接口”，改造成“Agent 手里的一把检索工具”。

## RAG 是什么，一句话回顾

RAG（检索增强生成）的意思是：先根据问题从知识库找到相关资料，再把资料和问题一起交给模型，让模型基于资料回答，而不是只靠模型脑内的记忆。

```
用户问题
  -> 检索：从知识库找最相关的片段（sources）
  -> 生成：把 sources + 问题 交给模型
  -> 回答：模型基于 sources 回答
```

好处有两个：

- 回答有依据，前端可以展示“来源”。
- 知识更新快：改文档就能改回答，不用重新训练模型。

模块 04 已经把“检索 + 生成”的链路跑通了。本模块的增量是把“要不要检索”这个决定权从用户手里，交到 Agent 手里。

## 为什么 RAG 要从“接口”变成“工具”

对比一下：

```text
模块 04 的 /ask：
  用户问 -> 后端无条件检索 -> 回答
  （检索是固定的，模型没有选择权）

模块 13 的 search_documents：
  用户问 -> Agent 判断要不要检索
         -> 需要：调用 search_documents，拿 sources
         -> 不需要：直接回答
         -> 检索不到：诚实说资料不足
```

变成工具后，“检索”不再是用户路径的一部分，而是 Agent 的能力清单之一。Agent 可以决定用不用、什么时候用、用了之后怎么回答。这和模块 01 学的工具调用是同一套机制，只是工具从“查套餐、创建工单”换成了“检索知识库”。

## Agent 怎么判断“要不要检索”

这是本模块的关键点，也是最容易被误解的地方。

### 真实项目：模型判断

真实项目里，后端把工具 schema 交给模型（function calling），模型根据用户问题语义判断：

```text
“公司的报销流程是什么？”  -> 需要检索，调用 search_documents
“你好”                    -> 不需要，直接回答
“什么是黑洞”              -> 需要检索，但知识库里没有，回答说明不足
```

模型是“语义级”判断，它能理解“报销流程”和知识库制度相关，“你好”和制度无关。

### 教学版 mock：关键词近似

mock 模式没有真实模型，用关键词近似判断，让链路稳定可复现：

```text
问题里出现“报销、请假、制度、流程、政策...”等知识词
或出现“是什么、怎么、如何、哪些...”等问句词
-> 触发检索
否则
-> 直接回答
```

mock 不聪明，但能让学习者稳定观察到“判断 -> 检索 -> sources -> 回答”的完整链路。切换到 DeepSeek 后，就是真实模型在判断。

## sources 是什么，为什么必须进入最终回答

`sources` 是检索到的相关片段。本模块里每个 source 长这样：

```json
{
  "chunk_id": 1,
  "document_id": 1,
  "chunk_index": 0,
  "content": "一、报销基本流程：员工发生费用后...",
  "document_title": "公司报销制度",
  "score": 2
}
```

`sources` 要进入最终回答，有两层意思：

1. **回答文本引用来源**：`reply` 里说“最相关的资料来自《公司报销制度》第 0 段”。
2. **接口返回 sources 字段**：前端可以单独展示“回答依据”，用户点开能看到引用原文。

真实项目里，没有 sources 的回答基本不算合格回答。因为用户会问“你凭什么这么说”，sources 就是回答的证据链。

## 检索不到资料时必须诚实说明

这是本模块最重要的验收点，也是真实 RAG 产品最常踩的坑。

模型有个致命缺点：**不知道就是不知道时，它倾向于编造**（幻觉）。如果把“没检索到资料”当成“正常情况”继续让模型回答，模型会一本正经地编一个答案。

所以后端必须显式处理空检索：

```text
sources 为空
-> 告诉用户：知识库中没有相关资料，不能凭想象回答
-> 建议补充文档，或换个说法再问
```

本模块 mock 和 DeepSeek 两个模式都做了这条路径。这是模块 04 没有做、但真实产品必须做的事情。

## 中文检索的难点：为什么教学版用 bigram

模块 04 的分词把一整句中文当成一个词：

```text
“报销流程是什么” -> 一个 token
```

结果就是：用户问“报销流程是什么”，和文档里的“报销流程”对不上，检索不到。这是关键词检索在中文上的真实短板（中文没有空格分词）。

本模块做了一个简化改进：把中文连续片段切成相邻双字（bigram）：

```text
“报销流程是什么” -> 报销、销流、流程、程是、是什么...
```

这样“报销”“流程”就能在文档里命中。缺点是有误匹配：比如“量子计算是什么”里的“计算”，会命中请假制度里的“年限计算”。这正是关键词检索“召回高、精度低”的典型问题，也是模块 14 为什么必须上 embedding 的原因。

教学上，bigram 让你先看到“检索会出错”这个真实问题，再理解 embedding 是为什么存在。

## 工具注册表、权限、审计：复用前面的能力

本模块不是重写，而是复用：

- `tool_registry.py`：工具白名单，模型只能从注册表里选工具。模块 10-12 学的，这里继续用。
- `permissions.py`：API Key 识别身份 + 后端权限兜底。本模块只有一个低风险读工具，所以权限检查简化了，但“后端不能只相信模型”这条原则保留。
- `ToolAuditLog`：谁在什么时候检索了什么、检索到什么，都留日志。

对比模块 12：本模块刻意**不引入**失败恢复执行器、人工确认、权限矩阵。不是因为它们不重要，而是本模块的核心是“RAG 怎么变成工具”，一次只学一件事。面试时能说明白“哪里简化了、为什么简化”比什么都堆上更难得。

## 真实项目通常怎么做

真实项目一般会：

- 用 embedding 模型把文档和问题转成向量，向量相似度检索，而不是关键词。
- 用向量数据库（pgvector、Milvus、Chroma 等）存 chunk，支持大规模检索。
- 模型通过 function calling 决定“要不要检索、检索词是什么、用哪个检索配置”。
- 检索结果带 metadata（部门、可见范围、文档类型），做权限过滤。
- 低置信度检索做 rerank，或者直接说明资料不足。
- sources 返回给前端，展示引用来源。
- 检索、工具调用、回答全部进日志，方便复盘回答质量。

## 教学版做了哪些简化

- 没有 embedding 和向量数据库，用中文 bigram 关键词近似。
- 检索是全表扫描，不是索引检索。
- mock 模式用关键词判断“要不要检索”，真实模式才用模型语义判断。
- 文档用 JSON 直接录入，没有文件上传和解析。
- 没有文档级权限隔离，所有角色能检索全部文档。
- 只有一个工具，没有多工具编排。

## 学完后能讲什么

你能讲：

- RAG 为什么在真实项目里是“工具”而不是“接口”。
- Agent 如何判断要不要检索，检索词从哪里来。
- sources 怎么进回答、怎么给前端展示。
- 检索不到时为什么必须诚实降级，而不是让模型编。
- 工具注册表、权限、审计如何和 RAG 组合。

## 本模块 4 个核心知识点

- RAG 检索要包装成工具，调用权交给 Agent。
- 工具调用必须走后端权限兜底，不能只信模型。
- sources 进入最终回答，回答必须有据可查。
- 检索为空时必须诚实说明不足，防止模型幻觉。

## 和前后模块的关系

- 前：模块 04 教 RAG 检索链路，模块 10-12 教工具注册表、权限、失败恢复。本模块把它们组合起来。
- 后：模块 14 把关键词检索升级成向量检索并加权限隔离；模块 15 把同样的“工具 + 决策 + 审计”模式用到数据库上。
