# Agent 记忆基础知识

## 1. 为什么 Agent 需要记忆

普通聊天接口通常只处理当前问题。用户问什么，模型答什么。

Agent 更像一个长期协作的助手。它不仅要完成当前任务，还要逐渐理解用户长期偏好，例如：

- 用户是初学者还是资深工程师。
- 用户希望回答偏理论还是偏就业实践。
- 用户喜欢中文、英文，还是双语。
- 用户正在做哪个长期项目。

这些信息如果每次都让用户重复说，体验会很差。如果全部依赖聊天历史，又会带来上下文过长、噪声过多、成本上升的问题。

长期记忆就是为了解决这个问题：把未来可能复用的信息从对话中提取出来，结构化保存，并在后续请求中按需检索。

## 2. 聊天历史不等于长期记忆

聊天历史保存的是原始消息。

例子：

```text
user: 我是 AI 应用初学者，以后请用中文回答，我喜欢就业级、企业级的讲解。
assistant: 好的，我会用中文并尽量结合企业级实践解释。
```

长期记忆保存的是结构化信息：

```json
[
  {"memory_type": "profile", "key": "learning_level", "value": "初学者"},
  {"memory_type": "instruction", "key": "reply_language", "value": "中文"},
  {"memory_type": "preference", "key": "learning_goal", "value": "偏向就业级、企业级内容"}
]
```

区别很关键：

- 聊天历史适合还原对话。
- 长期记忆适合未来复用。
- 短期状态适合记录一次 Agent run 的执行进度。

如果把所有聊天历史都当成记忆，Agent 会记住大量无价值信息，例如“我刚才打开了浏览器”“今天吃了什么”。这些信息不仅浪费上下文，还可能干扰回答。

## 3. 什么信息适合成为记忆

适合保存的信息一般满足至少一个条件：

- 未来可能反复影响回答。
- 用户明确表达了长期偏好。
- 能帮助 Agent 做个性化决策。
- 可以被结构化成稳定字段。

例子：

| 原始输入 | 是否适合记忆 | 原因 |
| --- | --- | --- |
| 我是初学者 | 适合 | 后续解释深度会受影响 |
| 以后请用中文回答 | 适合 | 属于长期交互指令 |
| 我喜欢企业级案例 | 适合 | 影响内容风格和案例选择 |
| 今天下雨了 | 通常不适合 | 大概率不会长期复用 |
| 这次订单号是 123 | 通常不适合 | 更像当前任务状态或业务数据 |

这里有一个工程判断：不是所有“真实信息”都应该成为长期记忆。

## 4. 记忆为什么要结构化

如果只保存一句自然语言：

```text
用户说自己喜欢就业级内容
```

后端很难稳定检索、更新和治理。

结构化后：

```json
{
  "memory_type": "preference",
  "key": "learning_goal",
  "value": "偏向就业级、企业级内容",
  "confidence": 0.84
}
```

程序就能做这些事：

- 按用户查询所有记忆。
- 按 `memory_type` 区分偏好、画像、长期指令。
- 按 `key` 更新同一类记忆。
- 按 `confidence` 判断是否需要人工确认。
- 后续做删除、过期、敏感信息过滤。

这就是为什么 Agent 记忆通常不是“把文本塞进数据库”。

## 5. 本模块的三类记忆

本模块只保留三类，便于初学者理解。

`profile`：用户画像。

例子：

- `learning_level = 初学者`
- `name = 小王`
- `role = 后端开发`

`preference`：用户偏好。

例子：

- `learning_goal = 偏向就业级、企业级内容`
- `likes:FastAPI = FastAPI`
- `dislikes:太抽象的解释 = 不喜欢太抽象的解释`

`instruction`：长期指令。

例子：

- `reply_language = 中文`

真实项目会更复杂，但早期不要分类过多。分类太多会让提取、检索和治理都变难。

## 6. 记忆写入链路

本模块 `/agent/chat` 的写入链路是：

```text
用户输入
-> 保存原始 user message
-> 提取 memory candidates
-> upsert 到 user_memories
-> 检索相关 memories
-> 生成回答
-> 保存 assistant message
```

这里的 `upsert` 很重要。

如果用户第一次说：

```text
以后请用中文回答。
```

系统保存：

```text
instruction / reply_language = 中文
```

后来用户又说：

```text
以后请用英文回答。
```

更合理的行为通常是更新 `reply_language`，不是插入两条互相冲突的记忆。

## 7. 记忆检索链路

后续请求不能把一个用户所有记忆都塞进模型。

原因：

- 记忆多了会占 token。
- 无关记忆会干扰回答。
- 敏感或过期记忆不应该默认进入上下文。

本模块用教学版规则打分：

- `instruction` 类记忆默认更容易被带入。
- 学习类问题更容易匹配学习画像。
- 推荐、选择、方案类问题更容易匹配偏好。
- query 直接包含 key 或 value 时加分。

真实项目可以升级成 embedding 检索、关键词检索、混合检索，但工程边界不变：

```text
先按 user_id 隔离
-> 再找相关记忆
-> 最后构造成模型上下文
```

## 8. 为什么要记录 memory 使用日志

`MemoryUseLog` 记录一次回答用了哪些记忆。

它回答的问题是：

- Agent 为什么这次用了“中文回答”？
- 为什么给这个用户推荐就业级内容？
- 某条错误记忆影响过哪些回答？

现在你可能觉得它只是多一张表。后续学习可观测性、评测、安全时，这类日志会非常重要。

## 9. 当前模块的限制

本模块为了教学清晰，故意保留一些限制：

- 记忆提取用规则，不是模型结构化输出。
- 检索用简单打分，不是向量检索。
- 没有删除记忆接口。
- 没有记忆过期。
- 没有敏感信息拒绝写入。
- 没有人工确认低置信度记忆。

这些不是遗漏，而是为了让你先学懂最小闭环。下一模块会进入记忆治理。
