# 工具失败恢复基础知识

## 本模块解决的真实工程问题

真实 Agent 工具常常依赖外部系统：

- CRM
- 工单系统
- 支付系统
- 邮件服务
- 文档检索服务
- 数据库

这些系统不稳定时，Agent 不能直接崩溃，也不能假装成功。后端要判断：

```text
这个错误能不能重试？
重试几次？
失败后有没有降级方案？
最终怎么解释给用户？
日志里怎么复盘？
```

这就是工具失败恢复。

## 三类常见失败

### 超时

例子：

```text
工单系统 3 秒没有响应
```

通常可以重试，但不能无限等。多次超时后可以降级到人工队列。

### 短暂失败

例子：

```text
第三方接口返回 503
网络短暂抖动
数据库连接池临时繁忙
```

通常适合有限重试。

### 永久失败

例子：

```text
参数格式错误
用户不存在
业务规则不允许
权限不足
```

通常不应该重试。重复调用只会浪费资源，甚至造成更多风险。

## 为什么不能无限重试

无限重试会导致：

- 接口长时间不返回。
- 外部系统被打爆。
- 用户不知道发生了什么。
- 日志被重复错误淹没。
- 成本和延迟不可控。

所以真实项目必须配置最大重试次数。

## 降级是什么

降级不是“假装成功”。

降级是主路径失败后，用一个更稳但能力更弱的方案兜底。

例子：

```text
主工单系统超时
-> 写入人工处理队列
-> 告诉用户：已进入人工处理，不是已经创建成功
```

本模块里的 `create_support_ticket_fallback` 就是教学版降级工具。

## 为什么永久失败不应该降级

如果失败原因是：

```text
参数错了
用户不存在
业务规则不允许
```

这不是外部系统暂时不可用，而是这件事本身不该执行。此时降级成“人工处理成功”会误导用户。

所以本模块规定：

```text
retryable=True 的失败才允许降级
permanent_error 不降级
```

## 工具函数和恢复执行器的区别

`tools.py`：

```text
负责单次工具执行
```

`recovery.py`：

```text
负责失败后怎么办
```

这是一种重要分层。不要把重试逻辑写进每个工具函数里，否则每个工具都会重复一套异常处理，很难统一排查。

## attempts 为什么重要

一次工具调用可能实际尝试多次：

```text
attempt 1: timeout
attempt 2: timeout
attempt 3: timeout
attempt 4: fallback success
```

如果接口只返回“成功”，用户会误以为主工具成功了。

所以 attempts 要记录：

- 第几次尝试。
- 调了哪个工具。
- 是否成功。
- 耗时多少。
- 错误码是什么。
- 是否会继续重试。

## 真实项目通常怎么做

真实项目会：

- 使用 HTTP 客户端 timeout。
- 对 429、502、503、504 这类错误做有限重试。
- 使用指数退避和随机抖动。
- 对参数错误、权限错误、业务拒绝不重试。
- 对可降级场景写队列或人工处理单。
- 记录 trace、attempt、耗时、错误码和成本。
- 给前端返回稳定错误结构。

## 教学版简化边界

本模块为了初学者先抓主链路，简化了：

- 不连接真实外部系统。
- 不真的等待超时。
- 用 `simulate_failure` 参数复现故障。
- 不实现指数退避。
- 降级工具只返回 mock 队列结果。
- 不实现熔断器。

## 学完后能讲什么

你能讲：

- Agent 工具为什么需要统一失败恢复层。
- 哪些错误应该重试，哪些不该重试。
- 降级和失败的区别。
- attempts 结构如何帮助前端展示和线上排查。
- 为什么确认单 approve 后也要复用同一套恢复执行器。

## 5 个核心知识点

- 工具失败要结构化，不要只抛异常。
- 重试只适合可重试错误。
- 重试必须有最大次数。
- 降级不能掩盖永久业务错误。
- 每次尝试都要可追踪。
