# 人工确认基础知识

## 本模块解决的真实工程问题

Agent 一旦接入工具，就不再只是“生成文本”。它可能真的改变业务系统。

例如：

- 修改用户套餐。
- 删除一批数据。
- 给客户发邮件。
- 发起退款。
- 创建高优先级工单。

这些操作的共同点是：执行后会改变外部世界。真实项目里，即使调用者是管理员，也不应该让模型一句话就直接执行。

所以需要人工确认。

## 权限和确认不是一回事

权限解决：

```text
这个用户有没有资格发起这个操作？
```

确认解决：

```text
这个具体操作要不要现在执行？
```

例子：

```text
admin 有权限修改套餐
但把 u_learner 从 free 改到 enterprise 仍然需要确认
```

上一模块解决“能不能调用工具”。本模块解决“有权限后，要不要立刻执行”。

## 什么是确认单

确认单是危险操作的快照。

它保存：

- 谁发起的。
- 要调用哪个工具。
- 工具参数是什么。
- 风险等级是什么。
- 当前状态是什么。
- 谁批准或拒绝。
- 执行结果是什么。

确认单的价值是把“模型想做的事”和“系统真正执行的事”隔开。

## 最小状态机

本模块使用 4 个状态：

```text
pending  等待确认
executed 批准后已执行成功
rejected 已拒绝，工具不会执行
failed   批准后执行失败
```

这不是为了写复杂代码，而是为了让真实项目能回答：

- 这个危险操作现在到哪一步了？
- 是还没人处理，还是已经拒绝？
- 如果失败，是批准失败还是执行工具失败？

## 为什么要保存参数快照

确认单里保存 `arguments_json`。

原因是：批准时必须执行“当时提交的参数”，不能重新让模型生成一遍参数。

如果批准时重新问模型，可能出现：

- 参数被改。
- 用户目标变化。
- 模型输出不稳定。
- 审计无法证明批准的到底是哪次操作。

所以真实项目一定要保存操作快照。

## approve 和 reject 的边界

`approve`：

- 只能由有权限的人调用。
- 只能处理 `pending` 状态。
- 批准后才执行工具。
- 执行成功变成 `executed`。
- 执行失败变成 `failed`。

`reject`：

- 只能由有权限的人调用。
- 只能处理 `pending` 状态。
- 不执行工具。
- 状态变成 `rejected`。

这个边界很重要：拒绝不是“执行一个取消工具”，而是根本不执行危险工具。

## DTO 和 ORM 怎么区分

本模块里：

- `PendingConfirmation` 是 ORM Model，对应数据库表。
- `ConfirmationResponse` 是 DTO，对应接口返回。
- `ConfirmationApproveRequest` 是 DTO，对应批准接口请求体。
- `ConfirmationRejectRequest` 是 DTO，对应拒绝接口请求体。

Java 类比：

- ORM Model 类似 Entity。
- DTO 类似 RequestDTO / ResponseDTO。

接口不要直接返回 ORM Model。这样以后数据库字段变化时，不会直接破坏前端接口。

## 真实项目通常怎么做

真实项目会更严格：

- 高风险操作必须确认。
- 特别高风险操作可能多级审批。
- 发起人不能批准自己的操作。
- 确认单有过期时间。
- approve 接口要有幂等键，避免重复执行。
- 工具执行要放进事务或可靠队列。
- 所有状态变化都写审计日志。

## 教学版简化了什么

本模块为了初学者先抓主链路，做了这些简化：

- 只演示一个高风险工具 `update_user_plan`。
- 只有 `admin` 可以 approve/reject。
- approve 后同步执行工具，不放后台任务。
- 没有幂等键。
- 没有过期时间。
- 没有真正接外部业务系统。

## 学完后能讲什么

你能讲：

- Agent 工具调用为什么要分成“发起”和“执行”。
- 高风险写工具为什么需要 pending confirmation。
- 确认单状态机如何设计。
- 审计日志如何记录批准、拒绝和执行结果。
- 为什么批准时必须执行保存下来的参数快照。

## 5 个核心知识点

- 权限检查决定能不能发起，人工确认决定能不能执行。
- 确认单是危险操作的持久化快照。
- 状态机保护重复批准、拒绝后执行等边界。
- approve 才执行工具，reject 不执行工具。
- 审计日志必须关联 request_id、confirmation_id 和工具结果。
