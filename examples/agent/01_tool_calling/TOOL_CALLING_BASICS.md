# Tool Calling 基础

## 工具是什么

在 Agent 场景里，工具就是后端程序暴露给模型使用的一组能力。

例如：

- 查天气。
- 计算订单金额。
- 检索公司制度。
- 查询数据库。
- 创建后台任务。

模型本身只会生成文本。它不能真的访问你的数据库，也不能真的运行你电脑上的函数。工具调用的真实含义是：

```text
模型提出调用请求，后端执行工具，后端再把结果交回给模型或直接返回给用户。
```

## 为什么需要工具

普通聊天适合回答常识性问题，但很多业务问题需要外部信息或确定性计算。

例如用户问：

```text
单价 19.9 元的商品买 3 个，用 SAVE10 优惠码，总价是多少？
```

模型可以口算，但口算不可靠。更好的方式是让模型调用 `calculate_order_total`，由后端用代码计算。

再比如用户问：

```text
报销制度是什么？
```

模型不应该凭空编。它应该调用 `search_policy` 去查资料。

## 什么是工具 schema

工具 schema 是给模型看的工具说明书。

它通常包含：

- 工具名称。
- 工具描述。
- 参数列表。
- 参数类型。
- 必填参数。

例如天气工具可以写成：

```json
{
  "name": "get_weather",
  "description": "查询一个城市的天气",
  "parameters": {
    "city": "城市名"
  }
}
```

如果没有 schema，模型就不知道：

- 有哪些工具可以用。
- 每个工具适合什么问题。
- 参数应该叫什么。
- 参数应该是什么类型。

## 参数从哪里来

参数通常来自用户问题。

用户说：

```text
深圳今天会下雨吗？
```

模型应该识别出：

```json
{
  "tool_name": "get_weather",
  "arguments": {
    "city": "深圳"
  }
}
```

也就是说，`city=深圳` 不是 FastAPI 路径参数，也不是查询参数，而是模型从用户文本里抽取出来的工具参数。

## 后端为什么还要校验参数

模型生成的参数不能完全信任。

它可能传错类型：

```json
{
  "quantity": "三个"
}
```

也可能传危险参数：

```json
{
  "tool_name": "delete_all_users"
}
```

所以后端必须做两件事：

- 只允许调用白名单里的工具。
- 每个工具内部继续校验参数。

本模块的 `tools.py` 里，`run_tool()` 就是工具白名单入口。

## 工具结果怎么进入最终回答

工具通常返回结构化数据。

例如：

```json
{
  "city": "深圳",
  "temperature": 30,
  "condition": "阵雨"
}
```

最终给用户看的回答不应该只是 JSON，而应该整理成自然语言：

```text
深圳当前教学版天气：30 摄氏度，阵雨。建议：建议带伞。
```

这一步可以由真实模型生成，也可以像本模块 mock 模式一样由后端手写规则生成。

## 工具调用不等于 Agent Loop

本模块只做一次工具调用。

完整 Agent Loop 会继续做：

```text
模型决策 -> 调用工具 -> 观察结果 -> 再决策 -> 再调用工具 -> 最终回答
```

这会放到下一模块 `examples/agent/02_minimal_agent_loop`。

现在先把单次工具调用看懂，否则一上来学循环会很容易混乱。
