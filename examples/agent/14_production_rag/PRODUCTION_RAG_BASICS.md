# 生产级 RAG 工程 · 基础知识

这份文档负责扫盲：RAG 在真实项目里到底要处理哪些问题，每个概念是什么、为什么存在、真实项目怎么做、本模块简化了什么。**它不是代码讲解**（代码讲解看 PRODUCTION_RAG_EXPLAINED.md），它的目的是让你先建立“这节在讲什么”的地图。

---

## 1. 为什么 RAG 需要“生产级”

模块 04 和模块 13 的 RAG 已经把核心链路跑通了：文档切分、入库、检索、带 sources 回答。但它离“能上线”还差很远，差在四件事：

1. **文档从哪里来**——真实项目里用户上传真实文件（txt/pdf/word），不是代码里手写的字符串。文件有编码、格式、损坏、超大小等一堆坑。
2. **文档有哪些“身份”**——真实知识库里文档有分类、标签、归属部门、可见范围。检索要知道“我只看财务类的”或者“我只能看自己部门的”。
3. **谁能看到哪篇文档**——多用户系统里，绝不能出现 A 检索到 B 的私有文档。这是数据安全底线。
4. **检索结果是否可信**——检索出的 top-k 真的都相关吗？把低相关片段喂给模型，模型会“自信地答错”。

一句话概括本模块：**把“能检索”变成“能上线”，补上解析、元数据、权限、排序、评测这五块工程能力。**

## 2. 核心概念逐个扫盲

### 2.1 文件解析（document_processor）

**概念**：把二进制文件（txt/pdf）变成干净的纯文本，这是 RAG 的输入。

**真实项目里的难点**：

- **编码**：中文 txt 可能是 UTF-8 也可能是 GBK。真实项目统一约定 UTF-8，但老文件会踩坑。
- **格式**：Word 要转文本，PDF 要提文本，扫描版 PDF 是图片必须 OCR。
- **脏内容**：页眉页脚、水印、导航栏、无意义字符都要清洗。
- **空文件 / 损坏文件**：必须明确报错，而不是“看起来成功了其实内容丢了”。

**工程原则**：宁可报错，不要静默失败。一个解析后为空文档的 PDF，如果被静默入库，检索会一直找不到它，而且排查困难。

**本模块简化**：只支持 txt/md/pdf。txt/md 标准库解码（UTF-8 失败回退 GBK），pdf 用 pypdf（纯 Python）。其余格式明确报 400。

### 2.2 文本切分（chunker）

**概念**：把长文档切成语义完整、长度适中的片段。检索的最小单位是 chunk，不是整篇文档。

**真实项目里的要点**：

- **语义完整**：尽量在段落/句子边界切，别从句子中间劈开。
- **重叠窗口（overlap）**：相邻片段保留一部分重叠，避免“正好把关键句切成两半”。
- **结构感知**：Markdown 按标题分节、按列表结构切，比固定长度效果好得多。
- **长度控制**：与后续 embedding / rerank 模型的最大输入长度匹配。

**为什么必须切**：大模型上下文有限；整篇文档匹配太粗糙；回答要能定位“原文第几段”。

**本模块简化**：段落优先，超长段落按句号/感叹号等句末标点再切，无重叠。默认 300 字/段。

### 2.3 metadata（元数据）

**概念**：描述“文档本身是什么”的附加字段，如分类、标签、作者、部门、上传时间。它和文档内容（正文）是两回事。

**metadata 和关键词检索的区别（重点）**：

| | metadata 过滤 | 关键词检索 |
|---|---|---|
| 性质 | 硬条件 | 软条件 |
| 作用 | 不符合直接排除 | 相关度打分 |
| 位置 | SQL 的 WHERE | 打分阶段 |
| 例子 | `category=财务` | “报销”在正文里出现几次 |

真实项目里 metadata 常存成 JSON 字段（PostgreSQL 的 JSONB），支持任意键值过滤。教学版简化成两个固定字段：`category`（分类）和 `tags`（标签）。

**为什么先过滤再打分**：过滤是把范围缩小（性能 + 准确率），打分是在缩小后的范围内排序。顺序反了会白白给无关数据打分。

### 2.4 文档级权限隔离（permissions）

**概念**：不同用户只能看到/检索到有权限的文档。这是本模块最重要的安全能力。

**关键认知：有两类完全不同的权限**

1. **工具权限**（模块 10-12 学的）：这个用户能不能调用某个工具。
2. **数据权限**（本模块学的）：这个用户能看到哪些数据（文档）。

真实项目里两者都要做。工具权限管“能不能查”，数据权限管“能查到什么”。

**为什么权限过滤必须在 SQL 层**：

- 只把“用户有权限的数据”从数据库查出来；
- 而不是把全库数据捞出来，再在内存里过滤。

原因一是性能（数据量一大内存就爆），二是安全（SQL 只返回有权限的数据，任何下游拿到都安全）。

**常见的数据权限模型**（真实项目）：

- RBAC：角色（管理员/普通用户）决定默认权限；
- 组织树：上级能看到下级的文档；
- 共享成员表：文档显式分享给特定用户；
- 部门/租户隔离：最常说的“多租户”，用租户 ID 隔离。

教学版简化成两级：`visibility=public`（所有人可见）或 `private`（owner 和 admin 可见）。规则收敛成一个布尔函数 `can_view_document(user, doc)`。

### 2.5 两阶段检索：召回 + 精排

**概念**：RAG 的检索不是一个步骤，而是两个步骤，业界叫“两阶段检索”或“retrieve-then-rerank”。

```
召回（Recall）：从全库快速找出 top-k 候选（要广、要快）
精排（Rerank）：对 top-k 逐条细看，只留 top-n 真正相关的（要准）
```

**为什么不能一步到位**：一步就想找到最相关的 N 条，意味着要拿 query 和全库每个 chunk 做精细对比，数据量大时太慢。先粗筛掉 99%，再精排剩下的 1%，速度和准确率都兼顾。

真实项目里：

- **召回**：embedding 向量检索（BM25 / 向量 / 混合检索），快、宽；
- **精排**：交叉编码器 rerank 模型（bge-reranker、Cohere Rerank），把 query 和 chunk 拼一起喂给模型打分，慢但准。

教学版：召回用 bigram 共现数量，精排用覆盖率/位置/标题/长度启发式打分。

### 2.6 rerank（重排序）

**概念**：对召回候选重新打分排序。核心问题：**“检索到”不等于“排得对”**。

**一个典型反例（本模块特意构造的）**：

查询“报销流程怎么走”时：

- 《公司规章制度大全》有一段 6 句话反复出现“报销”，共现的 bigram 数量很高，粗排会把它排到前面；
- 但它是泛泛的制度总述，并不是用户要的“报销流程”。

粗排看“共现字多不多”，所以被泛泛长文档骗了。精排看“覆盖率 + 位置 + 标题命中 + 长度”，把真正专门讲报销流程的段落提到最前。这就是 rerank 存在的意义。

**启发式打分为什么在教学里用**：真实 rerank 模型需要训练数据和算力。教学版用几个可解释的信号模拟它，让你理解“精排在综合什么信息”，而不是黑盒看分数。

### 2.7 相关性阈值（防幻觉的最后一道闸）

**概念**：检索结果必须过一道“相关性线”，低于线的片段不进回答。

**为什么必须有**：bigram 检索有大量“巧合匹配”。例如问题“产品路线图三季度**上线**什么功能”里的“季度规划”，和《员工请假制度》里“制度**规定**”共享 bigram“度规”。这种跨词巧合会让检索返回无关片段，模型再据此“自信地答错”。

**真实项目的做法**：

- 给检索打分设下限，低于阈值视为“无结果”；
- 回答策略分三种：命中（回答并引用 sources）、无料（诚实说资料不足）、无关（不触发检索）；
- 阈值需要标定：太低会混入噪音，太高会漏掉正确答案，一般用评测数据调。

**本模块的做法**：`RAG_MIN_SCORE`（默认 0.25）+ 覆盖率下限降权。修复后，bob 问机密问题会诚实回答“知识库中暂时没有找到相关资料”，而不是返回无关的请假制度。

### 2.8 RAG 评测前置数据

**概念**：一套固定的“问题 + 期望结果”数据集，用来回答“我改了检索/切分/rerank，到底变好没有”。

**真实项目的评测体系**（模块 21 会深入）：

- 指标：recall@n（期望文档是否出现在 top-n）、命中率、引用正确率、回答质量评分；
- 多版本对比：同一数据集跑改动前后，看指标变化；
- 线上回流：把真实用户问题沉淀成评测集，持续回归。

**本模块的做法**：`eval_cases.json` 存 6 个 case，`/eval/run` 跑出 recall@n。

**一个重要的设计点**：评测要带用户身份。同一个 case，admin 能看到私有文档、bob 看不到，recall 不同。这提醒你：评测要贴近真实权限环境，否则数字好看但实际不可用。

## 3. 本模块的完整链路图

```text
用户上传文件 (POST /documents/upload)
  -> document_processor.extract_text()   解析：字节 -> 纯文本（按扩展名选解析器）
  -> chunker.split_text()                切分：纯文本 -> 多个片段
  -> 写 documents + chunks 两张表         入库（一个事务，避免脏数据）

用户提问 (POST /search 或 /agent/chat)
  -> retriever.search_chunks()           检索：SQL 层权限过滤 + metadata 过滤 + bigram 粗排
  -> reranker.rerank()                   精排：覆盖率/位置/标题/长度综合打分
  -> 相关性阈值过滤                       低分巧合匹配挡在回答外
  -> rag._build_context()                拼带【来源】标记的上下文
  -> provider.run_agent_chat()           Agent 决策 + 生成带 sources 的回答
  -> 前端拿到 answer + sources            回答正文 + 依据
```

## 4. 真实项目 vs 本模块

| 维度 | 真实项目 | 本模块教学版 |
|---|---|---|
| 文件格式 | Word/PPT/Excel/扫描PDF(OCR)/网页 | txt/md/pdf |
| 切分 | overlap + 标题感知 + 语义切分 | 段落 + 句末标点，无 overlap |
| 召回 | 向量检索 / BM25 / 混合 | bigram 共现 |
| 精排 | 深度 rerank 模型 | 启发式打分 |
| 权限 | 组织树 + 共享表 + 租户 | public/private + owner |
| metadata | JSONB 任意键值 | category + tags 两个字段 |
| 评测 | 多指标 + 多版本 + 回流 | recall@n 单指标 |
| 相关性阈值 | 用评测数据标定 | 手工调 RAG_MIN_SCORE |

**必须理解的企业级方向**（面试重点）：权限隔离为什么在 SQL 层、metadata 和关键词的区别、两阶段检索、相关性阈值防幻觉、评测数据的价值。

**只要跑通示例的部分**（了解即可）：bigram 分词、启发式打分的具体权重、pypdf 解析细节。
