# 结构化输出基础知识

## 1. 为什么需要结构化输出

普通聊天接口返回的是自然语言，例如：

```text
这个订单大概率可以退款，建议先查询售后规则。
```

人能看懂，但后端程序很难稳定使用。后端真正需要的是：

```json
{
  "decision_type": "tool_call",
  "category": "refund",
  "priority": "medium",
  "confidence": 0.86
}
```

结构化输出解决的问题是：让模型回答从“给人读的一段话”变成“后端能继续处理的数据”。

在 Agent 项目里，这个能力非常重要。因为 Agent 往往不是回答完就结束，它还要：

- 判断下一步是否调用工具。
- 把任务分流给不同系统。
- 保存中间状态。
- 给前端展示标准字段。
- 给评测系统判断结果是否正确。

## 2. JSON 不等于输出可靠

初学者常见误区是：只要模型返回 JSON，就算结构化输出完成了。

这是不够的。

JSON 只解决“语法能不能解析”的问题。下面这段是合法 JSON：

```json
{
  "priority": "urgent",
  "confidence": "很高"
}
```

但它不一定符合业务契约：

- `priority` 可能只允许 `low / medium / high`。
- `confidence` 可能必须是 `0` 到 `1` 之间的数字。
- 必填字段可能缺失。
- 工具名可能不是后端白名单里的工具。

所以结构化输出至少分两步：

1. JSON 解析：字符串能不能变成 Python `dict`。
2. 契约校验：字段是否完整、类型是否正确、枚举是否合法、数值范围是否正确。

## 3. JSON Schema 是什么

JSON Schema 是一份“数据结构说明书”。

它会描述：

- 这个 JSON 应该有哪些字段。
- 字段类型是什么。
- 哪些字段是必填。
- 字段能不能取任意值。
- 数字范围是多少。
- 是否允许未知字段。

可以类比 Java 里的接口文档加 DTO 约束。不同的是，JSON Schema 通常可以被工具读取，也可以发给模型参考。

本模块的 `/output-schema` 就是把 `RefundDecision` 转成 JSON Schema。

## 4. Pydantic 在这里做什么

Pydantic 是 Python 里常用的数据校验工具。

在 FastAPI 里你已经见过 `BaseModel`。它既可以校验用户请求，也可以校验模型输出。

本模块里有两类 `BaseModel`：

- `StructuredRunRequest`：请求 DTO，校验用户传给接口的参数。
- `RefundDecision`：模型输出契约，校验模型返回的 JSON。

Java 类比：

- `StructuredRunRequest` 类似 Controller 的 request DTO。
- `RefundDecision` 类似模型服务返回给业务层的 response DTO。

注意：模型不是可信服务。即使它返回了文本，后端也要把它当成外部输入来校验。

## 5. Literal 为什么重要

`Literal["low", "medium", "high"]` 表示字段只能是这三个值之一。

这类似 Java enum。

它解决的问题是：防止模型临时发明业务系统不认识的值。

例如业务系统只支持：

```text
low / medium / high
```

但模型输出：

```text
urgent
```

如果后端不校验，后续统计、分流、页面颜色、告警规则都可能出错。

## 6. extra="forbid" 为什么重要

`ConfigDict(extra="forbid")` 表示不允许未知字段。

如果没有这个限制，模型多输出一个字段，Pydantic 可能会忽略它。忽略未知字段有时是可以接受的，但教学阶段应该先学严格契约。

严格契约的价值是：

- prompt 改动导致输出漂移时更容易暴露。
- 前端不会误以为某个临时字段稳定存在。
- 测试更容易发现模型行为变化。

## 7. 重试不是无限重试

模型输出不合法时，可以把错误反馈给模型，让它重试一次。

但不能无限重试。原因很简单：

- 每次重试都花 token 和时间。
- 错误可能不是模型能自己修好的。
- 接口不能无限等待。

所以本模块只允许最多两次尝试：

1. 第一次正常请求模型。
2. 如果失败，把解析或校验错误反馈给模型，再试一次。

如果第二次仍然失败，就降级。

## 8. 降级为什么也要结构化

坏设计是：

```json
{
  "error": "模型坏了"
}
```

这样前端和后续服务必须写一堆特殊判断。

更好的做法是：降级结果也符合同一份输出契约。

本模块降级时返回：

```text
decision_type = manual_review
risk_flags 包含 structured_output_failed
```

这样调用方仍然可以按同一个 `RefundDecision` 结构处理。

## 9. 企业项目里的常见落地方式

真实项目中，结构化输出通常会和这些能力组合：

- prompt 版本管理：不同版本的输出契约要同步测试。
- 工具调用：模型输出的工具名和参数必须二次校验。
- 上下文工程：只给模型足够的信息，减少胡乱补字段。
- trace 日志：保存原始输出、解析错误、校验错误。
- eval：固定样例集验证结构化结果是否稳定。
- 安全：避免把敏感数据放进错误信息或用户可见字段。

本模块只做最小闭环：输出契约、解析、校验、重试、降级。
